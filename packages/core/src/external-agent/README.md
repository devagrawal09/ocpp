Claude Code, Codex and Pi are session drivers. A driver runs a Session instead of the OC++ runner, using the user's own vendor CLI login or key. A Session's driver is the provider of its model: `claude/opus` is driven by Claude Code, `codex/sol` by Codex, `pi/anthropic/claude-sonnet-4-6` by Pi, and any provider model by the OC++ runner (`ocpp`). Choosing a driver is choosing a model, at creation (`session.create`) or later (`session.switchModel`), and the model variant is the vendor's reasoning effort. `GET /api/model/driver` lists each driver with its readiness, default model, suggested models and efforts; the web app offers the ready ones in the model picker.

A model alias always runs the vendor's newest model of that name. Claude Code resolves its own (`opus`, `sonnet`, `haiku`, `fable`). Codex has none, so OC++ derives them from Codex's catalog (`codex debug models`): `sol` is the newest listed `gpt-<version>-sol`, and likewise for every `gpt-<version>-<name>`. The Codex driver reads the catalog again at every run and resolves the alias there, so a Session on `codex/sol` moves to a new model as soon as Codex lists it; a pinned ID such as `gpt-5.6-sol` runs as named. The driver list offers the aliases and reports what each runs now. A subagent call reads the catalog too: it rejects an effort the resolved model does not support, and its result notes when a pinned model has a newer version or a vendor-named upgrade.

`SessionExecution` routes a vendor-driven Session to `ExternalAgentHarness` in the Session's Location. The harness is not a model provider inside `SessionRunner`: it owns its own drain. Prompts still enter through the durable inbox. At each boundary the harness promotes inbox items exactly as the runner does (steers first; at an idle boundary one queued item; compaction closes the vendor run and a move ends the drain), lowers the promoted messages as the runner would for a model (text, with image and PDF attachments in place), and delivers them to the vendor session. Vendor events project into the Session as ordinary assistant messages through `ExternalAgentStream`. A drain keeps its vendor session alive until the vendor is idle and every Code Mode execution it started has delivered its completion notification, so a vendor that launches work and waits is woken with the result. Claude receives steers and notifications mid-turn through streaming input (the CLI folds them in at its next boundary); Codex and Pi receive them when their turn ends.

## Compaction

Claude disables automatic, manual, and background vendor compaction through its environment and explicit settings. Pi disables threshold/overflow compaction before extension binding and rejects its manual compaction entry point. Codex has no hard disable control, so it remains available with best-effort compaction ownership, including in the native harness. Its normal auto-compaction threshold is raised to `Number.MAX_SAFE_INTEGER`; the independent full-context fallback can still compact.

OC++ is the preferred compaction owner. Manual requests run through `SessionCompaction`, which selects history, renders the summary prompt, publishes progress and usage, and commits the durable summary and instruction epoch. A fresh, tool-free vendor session generates the summary through the same login; it never resumes or checkpoints the conversation being compacted. The next conversational run starts a fresh vendor session from OC++'s canonical compacted history. A failed summary preserves the original context and vendor checkpoint.

When automatic compaction is enabled, a vendor context-overflow error allows one OC++ compact-and-rebuild attempt. A second unrecovered overflow stops the drain rather than looping. A completed automatic compaction is a durable continuation boundary for restart recovery. Claude or Pi compaction status is a policy violation: execution is aborted and its changed vendor history is not checkpointed as canonical. Codex vendor compaction is tolerated because its CLI cannot fully disable it.

## Attachments

Image (PNG, JPEG, GIF, WebP) and PDF attachments reach the vendor with the input they belong to: a prompt's files, a steer's or queued item's files, and the files a Code Mode run returns (for example `tools.read` of an image), which arrive with its completion notification. The bytes are the ones the runner sends a model: `toLLMMessages` lowers each attachment to a media part and `ProviderShared.normalizeMedia` gives its base64.

- Claude: Anthropic content blocks in the streaming-input user message, in message order: `image` blocks with a base64 source, and `document` blocks with a base64 PDF source titled with the file name. Text-only input stays a plain string. Claude Code keeps its own copy of each image and adds an `[Image: source: <path>]` line.
- Codex: `local_image` inputs. Each image is written to the run's temporary directory (the one that holds the OC++ harness instructions) and passed as `--image`; Codex reads it when the turn starts and keeps it in the thread as a data URL, so the directory is removed when the run ends and a later resume still has the image. Codex places images before the text, labelled `<image name=[Image #n] path=...>`. Input without any text gets `[Attached <names>]`, since Codex exec refuses an empty prompt. Codex has no PDF input: a PDF becomes the note `[Attached file report.pdf (application/pdf) was not forwarded: Codex takes only images]`.
- Pi: `prompt(text, { images })` with Pi's `ImageContent`; the images follow the text. Pi has no PDF input, so a PDF becomes the same note naming Pi. Pi itself replaces images with a placeholder for a model without image input.

## Harnesses

A top-level Session always runs in the OC++ harness. A subagent defaults to it and may ask for the native harness.

In the OC++ harness the vendor executes work through OC++'s full `execute` for that Session: the same Code Mode catalog (the Session's tool list), durable notebook, journaled calls and compile checks a native model gets, with each run's trace in the Session timeline. OC++ assembles the agent or OC++ prompt with its Code Mode rules, current instructions, catalog and subagent guidance through `SessionModelRequest.systemPrompt`. Codex and Pi receive that text as their system prompt; Claude receives it in the existing MCP execute tool's description. The durable notebook inventory in that text is a checkpoint fixed for the linked vendor session's lifetime: a resumed vendor session receives identical instructions and learns of later values from execution completion notifications, while a vendor session rebuilt from canonical history checkpoints the notebook as it then stands. A vendor's own compaction is not observed durably, so it does not refresh the checkpoint; `tools.notebook.list` remains available.

- Claude: a short generic coding-assistant system prompt directs it to follow the session instructions in `mcp__ocpp__execute`'s description. The full OC++ session instructions are appended unchanged to that description; no extra tool or bootstrap call is needed. `tools: []`, `settingSources: []`, `strictMcpConfig: true`, `skills: []`, the in-process `ocpp` MCP server as the only server, `allowedTools: ["mcp__ocpp__execute"]` and `permissionMode: "dontAsk"` keep native tools disabled. Claude Code still prepends one identity line ("You are a Claude agent, built on Anthropic's Claude Agent SDK.") and adds its own environment and token-budget `<system-reminder>` blocks to user turns. Instruction placement does not guarantee eligibility for subscription usage; Anthropic's billing rules still apply.
- Codex: every native tool feature off (`shell_tool`, `unified_exec`, `multi_agent`, `multi_agent_v2`, `view_image`, `browser_use*`, `in_app_browser`, `computer_use`, `image_generation`, `apps`, `plugins`, `remote_plugin`, `sleep_tool`, `tool_suggest`, `skill_search`, `skill_mcp_dependency_install`, `code_mode*`, `goals`, `memories`, `hooks`, `standalone_web_search`, `request_permissions_tool`), web search disabled, the OC++ prompt as `model_instructions_file`, Codex's apps, permissions, environment, collaboration and skills instructions off, the user's own MCP servers disabled (from `codex mcp list --json`), no project `AGENTS.md` (`project_doc_max_bytes = 0`), and a copy of Codex's model catalog without `tool_mode`, `multi_agent_version` or deferred tool search, so `execute` is offered directly instead of inside Codex's own code mode. The OC++ MCP server is approved (`default_tools_approval_mode = "approve"`) because exec mode cannot ask. What remains: `apply_patch` (it cannot be switched off; the `read-only` sandbox rejects every write), `list_mcp_resources`, `list_mcp_resource_templates` and `read_mcp_resource` (only the OC++ server is loaded and it has no resources), and `request_user_input` (Plan mode only). Known limit: Codex has no switch for the global `$CODEX_HOME/AGENTS.md`, so it still reaches the model as user instructions. Pointing `CODEX_HOME` at a scratch directory would need a copy of the user's credentials, and a token refresh there could rotate them and sign the user out of their own Codex. The bridge credential reaches Codex through `bearer_token_env_var` and its environment, never its command line.
- Pi: `noTools: "builtin"` (no read, bash, edit or write) with `execute` as its only custom tool, and a resource loader with no extensions, skills, prompt templates, themes or context files and the OC++ `systemPrompt`. Pi appends one "Current working directory" line.

In the native harness (subagents only) the vendor keeps its own tools, prompt and settings. OC++ adds its full `execute` over the tools the call passed, the call's `tool.define` handles and `submit_result` over MCP (or as Pi custom tools). OC++ does not authorize the vendor's native calls. Claude runs with the user's setting sources, `permissionMode: "default"` and its sandbox, and a `canUseTool` that allows whatever Claude Code would ask about, since nobody can answer; the user's own deny rules still apply. Codex runs in its `workspace-write` sandbox without network, with live web search. Pi keeps its own tools, extensions and settings. The Session timeline shows the vendor's native tool calls. Native Claude's sandbox needs `bubblewrap` and `socat` on Linux; without them Claude Code refuses with "Sandbox required but unavailable".

## Subagents

`tools.subagent` takes `tools`, `driver` (`ocpp`, `claude`, `codex`, `pi`) and `harness` (`ocpp`, `native`). `tools` is exactly the child's catalog: references and namespaces resolve against the caller's own catalog (`Tool.Context.catalog`), registry paths are published as `session-tools-selected`, and tools the caller only borrows (its `tool.define` handles and `init.ts` wrappers) are lent to the child for the call. Without `tools` a new child has none; a continued child keeps its list unless the call passes one, less any tool its caller no longer has (the result's `notice` names them). Unless the call names a driver, a continued child keeps its own, and a new child takes the driver of its agent's configured model (`claude/opus` selects Claude Code, any other provider the OC++ runner), else its caller's. `harness` defaults to `ocpp` for a new child; a continued vendor child keeps the harness its last subagent call ran it with (`session_external.harness`, recorded when a call activates the child or binds it) unless the call names one, and a direct prompt or a late notification still runs in the OC++ harness without changing it. `native` with the `ocpp` driver is refused. For Claude Code and Codex, `model` is the vendor's model name without a provider, with an optional effort after `#` (`opus#high`); for Pi it is Pi's `provider/model`. A model ID of the wrong shape fails before any vendor starts. Every other subagent input works unchanged: `input` and `inputSchema`, `tool.define` handles, `outputSchema` with `submit_result`, continuation by `sessionID`, and restart reattachment.

`root`, for every driver, places a new child in another existing absolute directory, such as a separate git worktree: its Location, with the project OC++ resolves for that directory, so the child runs under that directory's own config (agents, models, MCP servers, plugins, instructions), its runner or vendor harness works there, the paths the call passes must exist there by the same names, and a vendor gets an `execute` scoped to it. Its agent is resolved there: it must exist there, and its model there picks the default driver. Session tools (`tool.define` handles, `submit_result`, machine input) are shared by every Location (`ToolSessionTools`), so the child sees them. Roots compare by real path, so another spelling of the caller's (or a continued child's) directory keeps that Location and its workspace. A relative, missing, non-directory or unresolvable root fails as the call's error. A continued child keeps its directory, and a different `root` for it fails; sessions are never moved. A caller in a workspace cannot use another `root` until workspace placement is defined. A subagent call lends a vendor child its harness and tools while it holds the child (`ExternalAgentSession.activate`); it first lets a drain the child is already running on its own finish. Without a call, a vendor child drains like a top-level vendor Session, in the OC++ harness: a direct prompt or a late completion notification is answered.

Everything the call alone decides (input schemas, root shape, native with `ocpp`, an explicit vendor's readiness, model-name shape) fails before any child exists. A new rooted child's agent, default driver and tool paths are read from the root, which loads its plugins; a missing path fails the call before the child is created.

## Continuation

`session_external` keeps one vendor binding per Session: provider, directory, vendor session ID, the vendor-history checkpoint and the hash of the canonical history it answered. Canonical history is what the runner would show a model, reduced to text: messages, each tool call's name and input, and each result's model-visible content. An attachment in it is named where it was (`[Attached file shot.png (image/png), not re-sent]`), not sent again: the vendor answered it once, and replaying every image and PDF of a long Session into one message would outgrow what a vendor accepts. Tool metadata never enters it, so a Code Mode trace (with assignment values, private `input` and submitted output) never reaches a rebuilt vendor session, and a completion that rewrites the trace after the checkpoint does not force a rebuild. Binding again (another vendor, or a moved Session) starts a new vendor session. A drain resumes the vendor session only when both the canonical history hash and the vendor's own history fingerprint match the last checkpoint; otherwise it starts a new vendor session rebuilt from canonical OC++ history. Input the vendor never answered (for example the continuation prompt after a restart) is delivered again once, with its attachments. Startup recovery resumes the vendor Sessions a stopped process left running, like any other. User interruption aborts the vendor run; its partial step is recorded as interrupted.

## Readiness and configuration

A driver is ready when it is not disabled in `external_agents` and its CLI and login are present: `claude auth status`, `codex login status`, or a Pi provider with configured auth. Only the first probe is awaited; after five minutes its answer is still served while one background probe refreshes it, so no step waits on a vendor CLI. `OCPP_DISABLE_EXTERNAL_AGENTS=true` offers no drivers without probing (the core, server and CLI tests set it). A drain of an unready driver fails the Session with a message that says how to fix it. The web app lists ready drivers in the model picker but not among connected providers: their login belongs to the vendor CLI.

```json
{
  "external_agents": {
    "claude": { "enabled": true, "model": "sonnet", "effort": "high" },
    "codex": { "enabled": true, "model": "sol" },
    "pi": { "enabled": true, "model": "anthropic/claude-sonnet-4-6" }
  }
}
```

Pinned SDKs: Claude Agent SDK `0.3.266`, Codex SDK `0.153.4`, and Pi coding-agent SDK `0.85.1`. Codex's execution SDK lacks history reads, so a temporary app-server loads the exact persisted thread without prompting and reads complete legacy or paginated history. SDK imports are lazy; the workerd platform adapter offers no drivers.

Run deterministic tests from `packages/core`:

```sh
bun run test test/external-agent-harness.test.ts test/external-agent-driver.test.ts
bun typecheck
```

`test/external-agent-live.test.ts` is explicitly opt-in through `OCPP_EXTERNAL_LIVE=claude,codex,pi`. It sends real model requests through each SDK in the OC++ harness. Model overrides use `OCPP_EXTERNAL_LIVE_CLAUDE_MODEL`, `OCPP_EXTERNAL_LIVE_CODEX_MODEL`, or `OCPP_EXTERNAL_LIVE_PI_MODEL`.
